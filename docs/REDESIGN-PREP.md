# הכנה לשלב העיצוב מחדש של הלקוח

מסמך תכנון בלבד. **לא שונה שום קוד של הממשק.** נבדק מול הקוד הקיים ומול ה-API של השרת (commit `b3cf0ea` ואילך).

## 1. מצב קיים

| מסך / רכיב | קובץ | מה הוא עושה | נקודת חיבור לשרת |
|---|---|---|---|
| ניווט ו-session | `App.jsx`, `session.js` | טאבים `spots` / `mine` במצב (state) בלבד, token ב-`sessionStorage` | אין (401 מנקה session) |
| התחברות / הרשמה | `screens/AuthScreen.jsx` | טופס אחד לשני המצבים | `POST /api/tokens`, `POST /api/users` |

## 2. מה השרת כבר תומך בו ואינו מנוצל בלקוח

`GET /api/parking-spots` מקבל: `page`, `pageSize` (1-100), `floor`, `isActive`, `featureId`, `search` (עד 20 תווים), `date`, `available`, `sortBy` (`Code`/`Floor`), `sortDir` (`Asc`/`Desc`).
`api.js -> listSpots` שולח היום רק `page, pageSize, date, available, sortBy, sortDir`.

| סינון / יכולת | סטטוס בשרת | נדרש בלקוח |
|---|---|---|
| קומה | קיים (`floor`) | להוסיף פרמטר ב-`listSpots` + בקרה |
| מאפיין (מקורה, חשמלי...) | קיים (`featureId`), הרשימה ב-`GET /api/features` (לא מעומדת, קטנה) | קריאה חדשה `listFeatures` + בקרה |
| חיפוש לפי קוד | קיים (`search`) | בקרה + debounce |
| מיון לפי קוד / קומה, כיוון | קיים | בקרה |
| פעיל / לא פעיל | קיים (`isActive`), רלוונטי בעיקר ל-Admin | רק אם יהיה מסך Admin |
| פנוי בתאריך | קיים | כבר בשימוש |
| **סינון הזמנות** (סטטוס, טווח תאריכים, מיון) | **חסר בשרת**: `mine` ו-`GET /api/reservations` תומכים רק בעימוד, ממוינים לפי תאריך יורד | ראו סעיף 4 |
| חיפוש / סינון הזמנות לפי מקום או משתמש (Admin) | **חסר בשרת** | ראו סעיף 4 |
| מיון לפי "פנוי/תפוס" | לא קיים (דורש מיון על חישוב תלוי תאריך) | מומלץ לא לדרוש; אפשר "פנויים קודם" בצד לקוח בתוך עמוד בלבד, לא מומלץ |

## 3. נקודות ללקוח שנמצאו בבדיקה (לא תוקנו, כי אין שינוי בממשק בשלב הזה)

אומתו בקריאת הקוד:
1. `SpotsScreen.load` ללא ביטול בקשות: שתי בקשות מהירות (שינוי תאריך/עמוד) עלולות להחזיר בסדר הפוך ולהציג תוצאה ישנה. בעת הוספת סינונים הסיכון גדל. פתרון: `AbortController` או מונה בקשות.
2. תאריך ריק (המשתמש מחק את השדה): `buildQuery` מדלג על הפרמטר, והכותרת מציגה "מצב ב-". פתרון: לא לטעון, או ברירת מחדל.
3. הטאב הנוכחי והסינון אינם נשמרים ברענון (אין router ואין URL state). רענון מחזיר ל"מקומות חניה". פתרון: React Router או query string.
4. `Pagination` ו"עמוד מעבר לאחרון": אחרי סינון שמצמצם תוצאות, `page` נשאר (השרת מחזיר רשימה ריקה עם `totalPages`). פתרון: איפוס עמוד בכל שינוי סינון (כבר נעשה עבור תאריך ו"פנוי"), ותיקון עמוד אם `page > totalPages`.
5. אין מסכי Admin: ניהול מקומות (`POST/PUT/DELETE /api/parking-spots`) ורשימת כל ההזמנות (`GET /api/reservations`) קיימים בשרת בלבד.
6. תפוגת token (30 דקות) מתגלה רק בקריאה הבאה (401 -> התנתקות). אפשר להוסיף בדיקת `exp` מראש.
7. תגובת 429 (הגבלת קצב בהתחברות) מוצגת כהודעת השרת (`title`), וזה תקין. כדאי לעצב אותה ולהציג `Retry-After` אם ירצו.
8. תוויות סטטוס במילון קשיח (`Active`, `Cancelled`); יש להרחיב אם יתווספו סטטוסים.

חשד שדורש בדיקה בדפדפן בזמן העיצוב: RTL עם מספרים שליליים (קומות מרתף) - כיום עטוף ב-`<bdi>`.

## 4. דרישות שרת אפשריות (לא בוצעו; שינוי תוסף בלבד, בלי שינוי חוזה קיים ובלי מיגרציה)

**4.1 סינון ומיון הזמנות** (`GET /api/reservations/mine` ו-`GET /api/reservations`)
- פתרון: מחלקה `ReservationQuery : PaginationQuery` עם פרמטרים אופציונליים: `status` (`Active`/`Cancelled`), `from`, `to` (תאריכים), `sortDir` (`Asc`/`Desc`, ברירת מחדל `Desc` כמו היום). ל-Admin גם `spotCode` / `userId`.
- תאימות לאחור: בלי פרמטרים, התוצאה זהה להיום. אין שינוי טבלאות. קיים אינדקס על התאריך (`AddReservationDateIndex`), ולכן אין צורך באינדקס חדש.
- בדיקות נדרשות: יחידה לסינון (Repository על PostgreSQL זמני), גבולות (`from > to` = 400), HTTP.

**4.2 מאפיינים מרובים** (למשל "מקורה וגם חשמלי")
- היום `featureId` יחיד. פתרון: `featureIds=1&featureIds=2` עם AND. תוספת תואמת לאחור (הפרמטר הקיים נשאר).

**4.3 מיון לפי זמינות**: לא מומלץ, כי תלוי תאריך ומחייב שאילתה יקרה יותר; אם יידרש, להוסיף `sortBy=Availability` רק יחד עם `date`.

**4.4 הגבלת קצב**: ברירת מחדל 10 בקשות הרשמה/התחברות לדקה לכל IP. בהדגמה מרשת משותפת אפשר להגדיל עם `RateLimiting__AuthPermitLimit`.

## 5. סדר עבודה מוצע לשלב העיצוב
1. אישור שצד השרת יציב (ואם רוצים, ביצוע 4.1 קודם, כי זה משפיע על מסך "ההזמנות שלי").
2. הרחבת `api.js` (`listSpots` עם כל הפרמטרים, `listFeatures`) + עדכון `api.test.js`. השמירה על הבדיקות הקיימות.
3. router או שמירת מצב ב-URL (סעיף 3.3), ואז עיצוב המסכים.
4. הרצה חוזרת של `npm test`, `npm run e2e` ובדיקת הדפדפן (`scripts/e2e.mjs`, ובדיקת Edge) אחרי כל מסך.
